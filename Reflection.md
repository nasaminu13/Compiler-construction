Reflection
Q1. Implementing the scanner helped me understand how source code is broken down into smaller units called tokens before later stages of compilation. I learned that the scanner needs to examine the input character by character and decide what kind of token each character or sequence represents. The scan_token method uses a match statement to distinguish between symbols, operators, numbers, strings, whitespace, and invalid characters (src/scanner.rs:45-56). I also learned the importance of keeping track of the current line, especially when scanning strings that may span multiple lines. The string scanner checks for newline characters and increments the line counter when necessary (src/scanner.rs:128-134). Another important lesson was handling errors without stopping the entire scanning process. For example, an unterminated string is reported through the scanner's error mechanism (src/scanner.rs:136-138). Overall, this task gave me a better understanding of how a lexer works internally.

Q2. One of the more challenging parts was correctly handling string literals because they can contain multiple characters and may extend across lines. The scanner first recognizes the opening quotation mark and calls the string-scanning function (src/scanner.rs:48-56). The string function then continues advancing through the source until it reaches another quotation mark or the end of the input (src/scanner.rs:125-134). I had to make sure that newlines inside strings were handled correctly so that the scanner's line number remained accurate. Another challenge was dealing with an unterminated string. Instead of attempting to create an invalid token, the scanner records an error and returns (src/scanner.rs:136-138). I also learned that implementing a function is not enough; it must actually be connected to the scanner's token-recognition logic. The " case in scan_token is what makes the string scanner reachable (src/scanner.rs:56). This reinforced the importance of integration when building compiler components.

Q3. If I were improving the scanner further, I would focus on making the implementation more complete, maintainable, and robust. One improvement would be expanding the scanner's support for identifiers and keywords so that it can recognize names in the source code instead of treating unsupported characters as errors. The current implementation already has an identifier function planned for this purpose, showing where that functionality can be developed next (src/scanner.rs:162-166). I would also add more comprehensive tests for string literals, particularly strings containing multiple lines, empty strings, and unterminated strings. The current implementation already tracks newlines while scanning strings (src/scanner.rs:128-134) and reports an error when a closing quotation mark is missing (src/scanner.rs:136-138), so these behaviors could be verified systematically with tests. Finally, I would continue improving error messages so that they provide useful information about where and why scanning failed. This would make debugging later compiler stages easier.
